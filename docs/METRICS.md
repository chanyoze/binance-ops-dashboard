# 지표 선정 근거

과제는 *"어떤 지표를 왜 선정했는지"* 를 명시적으로 요구했습니다. 이 문서가 그 답입니다.

---

## 0. 이 대시보드의 사용자는 누구인가

지표를 고르기 전에 사용자를 정해야 했습니다.

> **트레이더가 아니라 데이터 수집 팀 엔지니어입니다.**

이 사람이 화면 앞에서 하는 판단은 두 가지입니다.

1. **이 데이터를 믿어도 되는가** — 파이프라인이 살아 있는가, 구멍은 없는가
2. **시장이 지금 어떤가** — 가격·거래량·체결 주도권

그래서 **시장 지표와 운영 지표를 함께** 놓습니다. "실사용 포맷 vs 수집 증명"은
이분법이 아닙니다 — 실무 데이터 팀 대시보드가 정확히 둘 다인 형태입니다.

그리고 순서가 있습니다. **운영이 먼저입니다.** Data Lag 가 틀어지면 화면의 나머지
지표는 전부 거짓말이 됩니다. 그래서 화면이 "이 데이터를 믿어도 되는가"로 시작합니다.

---

## 1. 운영 지표 — 파이프라인의 건강

### Data Lag (초) — 이 화면의 Hero

**정의**: `now() - collector_state.last_message_at` 중 **가장 뒤처진 심볼**의 값.

**왜 이것이 첫 번째인가**: 운영에서 단일 최상위 지표입니다. 이 값이 튀면 나머지 지표가
전부 오래된 값이 되는데, 화면은 아무 일 없다는 얼굴을 합니다. 조용히 틀리는 것이
시끄럽게 죽는 것보다 나쁩니다.

**왜 최댓값인가**: 평균을 내면 한 심볼이 완전히 죽어도 다른 쪽이 가려 줍니다.
가장 나쁜 쪽이 이 화면의 상태입니다.

**연결 판정은 반대로 최솟값**: "연결됐는가"까지 최악값으로 판정하면 잠시 조용한 심볼
하나 때문에 화면 전체가 '연결 끊김'으로 뒤집힙니다. 심볼 하나가 조용한 것과
소켓이 죽은 것은 **다른 사건**입니다.

**서버에서 계산합니다.** 브라우저가 `Date.now() - lastMessageAt` 으로 구하면 보는 사람
PC 시계가 틀어진 만큼 운영 지표가 틀어집니다.

| 임계 | 상태 | 색 |
|---|---|---|
| < 3s | 정상 | good |
| 3 ~ 10s | 주의 | warning |
| 10 ~ 30s | 경고 | serious |
| > 30s | 위험 | critical |

### 데이터 커버리지 (%)

**정의**: `실제 적재 봉 수 / 기대 봉 수 × 100`. 분모는 **첫 봉 ~ 마지막 봉** 구간입니다.

**왜 필요한가**: 데이터 완전성 SLA 입니다. Data Lag 가 "지금 신선한가"를 말한다면,
커버리지는 "여태까지 빠짐없이 모았는가"를 말합니다. 둘은 다른 질문입니다 —
방금 재시작해서 lag 는 0 인데 어제 구간에 구멍이 있을 수 있습니다.

**분모를 `now` 가 아니라 마지막 봉으로 잡는 이유**: 수집 시작 전 구간까지 결손으로 세면
**서비스를 늦게 켠 것이 데이터 품질 문제로 보입니다.** 지표가 사실과 다른 말을 하면 안 됩니다.

**형태는 미터(meter)**: 한계선 100% 대비 단일 비율이라 2조각 파이 차트를 쓸 자리가 아닙니다.

### 갭 복구 (봉)

**정의**: `backfill_completed` 이벤트의 `written` 합. 단 **`reason='initial'` 은 제외**합니다.

**제외하는 이유**: 최초 적재는 "복구"가 아닙니다. 넣으면 심볼당 1,441봉이 복구량으로
잡혀 **자가 치유가 실제로 몇 봉을 메웠는지가 안 보입니다.** (목업 단계에서 이 값이
2,900봉으로 나와 발견했습니다.)

이 숫자가 Part 1 의 자가 치유 설계가 실제로 동작했다는 증거입니다.

### 재연결 횟수

**정의**: `collector_state.reconnect_count` 합.

네트워크 불안정의 조기 신호입니다. 커버리지가 100% 여도 재연결이 잦으면
그 구간은 백필이 메운 것이고, 언제든 메우지 못하는 상황이 올 수 있습니다.

### WS / REST 봉 수

**정의**: `klines.source` 별 개수.

실시간 수집분과 백필분의 비입니다. **백필이 실제로 동작했다는 것을 데이터로 증명합니다.**
REST 비율이 갑자기 늘면 실시간 경로에 문제가 생겼다는 뜻입니다.

### 수신 체결 (건/초)

**정의**: 최근 5개 확정 봉의 `trade_count` 합 / 60 / 봉 수. **전 심볼 합계**입니다.

스트림 정상성입니다. 0 으로 떨어지면 좀비 연결을 의심해야 합니다.
(라벨에 "전 심볼 합"을 명시했습니다 — 지표가 무엇을 세는지 화면이 말해야 합니다.)

### Uptime

**정의**: `now() - collector_state.ws_connected_since`.

현재 WS 연결이 얼마나 유지되고 있는지. Binance 는 24시간마다 연결을 강제 종료하므로
이 값이 24시간 근처에서 리셋되는 것은 정상입니다.

### 파이프라인 이벤트 로그

연결·재연결·갭 감지·백필 시작/완료·좀비 감지·오류가 시각과 함께 쌓입니다.

**차트가 아니라 테이블인 이유**: 7종이 넘는 분류가 **모두 의미를 가집니다.**
차트로 만들면 색을 7개 만들어야 하고, 그러면 색이 의미를 잃습니다.
그리고 여기서 읽어야 하는 것은 추세가 아니라 **개별 사건의 내용**입니다
(`restart · 3봉 · 116ms`).

## 2. 시장 지표

### 캔들스틱 + 거래량

가격 흐름 파악의 기본형이고, 동시에 **수집 데이터의 신뢰성을 시각적으로 검증**하는
수단입니다. 봉이 빠지거나 이상한 값이 섞이면 눈에 보입니다.

거래량을 함께 두는 이유 — **거래량 없는 가격 변동은 노이즈**입니다.
가격만 보면 의미 있는 움직임과 얇은 호가창에서 일어난 튐을 구분할 수 없습니다.

인터벌은 1m / 5m / 15m / 1h 를 전환합니다. 1분봉만 저장하고 나머지는 SQL 로 접습니다
([ARCHITECTURE.md §6](ARCHITECTURE.md)).

### 현재가 · 24h 변동률

**단일 현재값 + 변화**이므로 차트가 아니라 **stat tile** 입니다.
막대 하나짜리 차트는 정보를 더하지 않고 공간만 씁니다.

**현재가는 두 곳에서 나옵니다.** 큰 숫자는 aggTrade 틱 가격(최대 60초 신선),
24h 변동률·고저는 봉 기준입니다. 출처가 다르다는 것을 알고 섞었습니다.

### VWAP (거래량 가중 평균가)

**정의**: `Σ quote_volume / Σ volume` (24h).

**왜 단순 평균이 아닌가**: 기관 체결의 기준선입니다. 현재가가 VWAP 위에 있으면
그날 산 사람들의 평균보다 비싸다는 뜻이고, 그 괴리가 과열/침체의 신호가 됩니다.
종가의 단순 평균은 거래가 거의 없던 시각의 가격을 활발한 시각과 같은 무게로 셉니다.

### 이동평균 (MA20)

추세 방향과 지지·저항. **접은 뒤에 계산합니다** — 1분봉에서 MA20 을 구해 5분봉에 붙이면
"최근 20분 평균"이 되어 화면이 말하는 MA20(=최근 100분)과 다른 값이 됩니다.

MA60 은 넣지 않았습니다. 120봉 화면에서 절반이 잘려 선이 끊긴 채로 보입니다.
필요하면 `getCandles(..., maPeriod)` 인자만 바꾸면 됩니다.

### Taker 매수 비율

**정의**: `Σ taker_buy_quote / Σ quote_volume` (24h). **금액 기준**입니다.

**왜 이 지표인가**: Taker 는 시장가로 밀어붙인 쪽입니다. 호가를 걸고 기다린 게 아니라
지금 당장 체결시키려 한 쪽이므로, 이 비율이 **체결 주도권**을 말합니다.
가격에 선행하는 신호로 읽힙니다.

**왜 수량이 아니라 금액인가**: 수량 기준이면 가격대가 다른 구간의 체결이 같은 무게로
섞여 "얼마어치가 매수였나"를 답하지 못합니다.

**개별 체결(aggTrade)을 저장하지 않고도 계산됩니다** — Binance 가 kline 안에
`takerBuyBaseVolume` 으로 이미 집계해서 줍니다 ([ARCHITECTURE.md §7](ARCHITECTURE.md)).

**형태는 diverging bar (50% 중심)**:
읽어야 할 것은 "부분 대 전체"가 아니라 **"50% 기준선의 어느 쪽인가"** — 폴라리티입니다.
도넛은 두 부채꼴의 면적을 눈으로 비교하게 만듭니다. 50% 를 중심으로 좌우로 뻗는
막대가 "지금 매수 우위"를 0.2초에 읽히게 합니다.

**축 반폭은 ±15%p** 입니다. ±100%p 로 잡으면 실제 값(대체로 44~52%)이 전부
중앙 1px 에 뭉개져 **아무것도 안 보입니다.** 목업을 눈으로 보고서야 잡힌 문제이고,
축을 좁히는 대신 양 끝에 범위를 적어 눈금을 속이지 않습니다.

### BTC / ETH 상대 강도 — 구간 시작 = 100 으로 지수화

**이 과제가 깔아둔 함정을 우회하는 지점입니다.**

BTC 는 약 $64,000, ETH 는 약 $1,890 — **스케일이 30배 차이납니다.** 한 차트에 그리려면
y축을 두 개 만들고 싶어지는데, 그러면 두 선의 교차점이 **아무 의미도 없는데 의미처럼
보입니다.** 축 눈금을 어떻게 잡느냐에 따라 "ETH 가 BTC 를 추월했다"는 착시를
임의로 만들어낼 수 있습니다.

```sql
100.0 * close / first_value(close) OVER (PARTITION BY symbol ORDER BY bucket)
```

구간 시작을 100 으로 정규화하면 두 선이 **같은 축**에서 "구간 시작 대비 몇 % 움직였나"로
비교됩니다. 축이 하나이므로 교차점이 진짜 의미(구간 수익률 역전)를 갖습니다.

**두 심볼이 모두 값을 가진 버킷에서만 기준을 잡습니다.** 한쪽만 있는 구간에서 100 을
정하면 두 선의 출발점이 어긋나 비교 자체가 거짓이 됩니다.

## 3. 형태(form)를 어떻게 골랐나

"무엇을 보여줄까"가 아니라 **"읽는 사람이 무슨 판단을 해야 하는가"** 로 정했습니다.
**때로는 정답이 차트가 아닙니다.**

| 데이터 | 읽는 사람의 과제 | 채택 | 쓰지 않은 것 |
|---|---|---|---|
| 현재가 + 변동률 | 단일 현재값 + 변화 | stat tile | ~~막대 1개짜리 차트~~ |
| Data Lag | 단일 현재값 + 추세 | stat tile + 스파크라인 | — |
| 커버리지 | 한계선 대비 비율 | meter | ~~2조각 파이~~ |
| 가격 흐름 | 시간에 따른 추세 | 캔들스틱 | — |
| 거래량 | 시간대별 크기 비교 | 컬럼 (캔들 하단) | — |
| Taker 비율 | 기준선의 어느 쪽인가 | **diverging bar** | ~~도넛/게이지~~ |
| BTC vs ETH | 서로 다른 시리즈 비교 | 멀티라인 (지수화) | ~~이중 축~~ |
| 이벤트 이력 | 개별 사건의 내용 | 테이블 | ~~색을 7개 만들기~~ |

결과적으로 **통계 카드가 차트보다 많습니다.** 의도된 결과입니다 —
운영 대시보드에서 읽히는 값의 상당수가 단일 현재값이기 때문입니다.

## 4. 색 — 눈으로 고르지 않고 계산했다

모든 색은 정확히 네 역할 중 하나만 합니다. 역할을 섞으면 무너집니다.

| 역할 | 이 대시보드에서 | 배정 |
|---|---|---|
| **Categorical** (정체성) | BTCUSDT / ETHUSDT | slot 1 파랑 · slot 2 주황 (고정 순서) |
| **Sequential** (크기) | 커버리지 미터 | 단일 색상 램프 |
| **Diverging** (폴라리티) | Taker 매수/매도 편향 | 파랑 ↔ 빨강, 중앙 중립 |
| **Status** (상태) | 연결 상태 · Lag 심각도 | good / warning / serious / critical **고정** |

**핵심 규칙 — 한 차트 안에서 정체성과 폴라리티를 동시에 색으로 인코딩하지 않습니다.**
파랑이 "BTC"이면서 동시에 "상승"일 수는 없습니다. 그래서:

- **캔들 차트** — 한 번에 심볼 하나만 표시(제목이 심볼을 말함) → 색은 전부 폴라리티
- **상대 강도 차트** — 두 심볼 동시 표시 → 색은 전부 정체성. 등락색을 안 씁니다
- **stat tile** — 델타 텍스트에만 폴라리티 색. 심볼 식별은 라벨이 담당

status 색은 **절대 "시리즈 4번"으로 재사용하지 않습니다.** 항상 아이콘 + 라벨과 함께 나갑니다.

### 트레이딩 관례인 초록/빨강이 검증에서 탈락했다

색을 눈으로 판단하지 않고 대비 검증기를 돌렸습니다.

```
$ node validate_palette.js "#0ca30c,#d03b3b" --mode dark --surface "#1a1a19"

  [PASS] Lightness band         all 2 inside L 0.48–0.67
  [PASS] Chroma floor           all 2 >= 0.1
  [FAIL] CVD separation         worst adjacent #d03b3b↔#0ca30c ΔE 4.1 (deutan)
  [PASS] Normal-vision floor    worst adjacent ΔE 33.9 (normal)
  [PASS] Contrast vs surface    all 2 >= 3:1
  → FAILED
```

정상 시각에서 초록과 빨강은 ΔE 33.9 로 아주 잘 구분됩니다. 그런데
**적록색약(deuteranopia)에서는 ΔE 4.1** 로 무너집니다. 기준선이 8(목표)/6(최저)이므로
**최저선조차 못 넘는 하드 실패**입니다.

한국 남성의 약 5~6% 가 적록색약입니다. 즉 **상승과 하락이 구분되지 않는 사용자가
20명 중 1명꼴**로 존재합니다. 가격 대시보드에서 이건 불편이 아니라 판단 오류를 유발하는
결함입니다.

**대응 — 관례를 버리지 않으면서 결함을 제거합니다.**

초록/빨강을 무조건 버리는 것은 답이 아닙니다. Binance·TradingView 등 모든 거래소가
쓰는 관례라 바꾸면 오히려 학습 비용이 생깁니다. 대신 **색이 유일한 정보 채널이 되지
않게** 합니다.

| 대상 | 조치 |
|---|---|
| 캔들 차트 | 초록/빨강 유지. **몸통의 시가·종가 위치라는 기하 인코딩이 이미 있어** 색이 유일 채널이 아닙니다 |
| 등락률 숫자 | **부호(+/−) 항상 명시 + ▲▼ 병기.** 색 없이도 읽힙니다 |
| Taker diverging bar | **파랑↔빨강.** 여기는 관례가 없고 색이 유일 채널이라 검증 통과 팔레트를 씁니다 |
| 상태 배지 | status 팔레트 + **아이콘 + 텍스트 라벨 필수** |

최종 팔레트는 다크 모드 기준으로 검증을 통과했습니다.


## 5. 화면 배치 — 왜 이 순서인가

```
┌──────────────────────────────────────────────┐
│ PIPELINE HEALTH            ● connected 34m   │  ← 이 데이터를 믿어도 되는가
│  1.47s    100.00%    18봉     87/s           │

├──────────┬────────┴──┬───────────────────────┤
│ 상대 강도  │ Taker 비율 │ 파이프라인 이벤트      │  ← 비교 · 왜 그렇게 됐나
└──────────┴───────────┴───────────────────────┘
```

위에서 아래로 읽는 순서가 판단의 순서입니다.

**Hero 는 뷰당 정확히 하나**이고 Data Lag 를 올렸습니다. 이 화면이
"이 데이터를 믿어도 되는가"로 시작하는 것이 Part 1(안정적 수집)과 Part 2(대시보드)를
하나의 서사로 잇습니다. 시세는 바로 아래 캔들에서 충분히 보입니다.

**스크롤이 없어야 한다**가 1순위 제약입니다. 운영 대시보드는 모니터에 띄워두고
흘끗 보는 화면이고, 스크롤하는 순간 운영 도구가 아니게 됩니다.
1600×900 과 1366×768 두 해상도에서 확인했습니다.
