# AI 활용 방식

이 문서는 "AI 로 이만큼 만들었다"가 아니라 **무엇을 맡기고 무엇을 직접 판단했는지의
경계**를 씁니다. 그 경계가 흐리면 결과물의 어느 부분을 믿어야 할지 알 수 없기 때문입니다.

사용 도구: Claude (Claude Code)

---

## 1. 경계 — 무엇을 맡기고 무엇을 직접 정했나

| 직접 판단한 것 | AI 에게 맡긴 것 |
|---|---|
| **문제 정의** — 세 요구가 사실 한 문제라는 판단 (`ensureRange` 통합) | 그 결정을 구현하는 코드 |
| **스키마 설계** — 무엇을 키로 둘지, `source` 컬럼을 왜 두는지 | 마이그레이션 생성, 타입 정의 |
| **장애 시나리오 도출** — 좀비 연결이 가장 위험하다는 판단 | watchdog 구현, 백오프 계산 |
| **버퍼를 두지 않는다는 결정** — 원본이 Binance 에 있다 | — |
| **지표 선정과 형태** — 무엇을 왜 보여줄지 | SVG 차트 구현 |
| **레이아웃 확정** — 세 안을 비교해 고른 것 | 세 안의 목업 제작 |
| **트레이드오프 수용 여부** — 무엇을 포기할지 | 선택지 정리, 검증 실행 |
| 커밋 단위와 커밋 메시지의 논지 | 문장 다듬기 |

한 문장으로: **"무엇을 왜"는 직접 정하고, "어떻게"를 맡겼습니다.**
그리고 맡긴 결과를 **검증하는 장치를 만드는 데** AI 를 가장 많이 썼습니다.

---

## 2. 판단을 맡긴 게 아니라 검증을 자동화했다

이 프로젝트에서 AI 활용의 핵심은 코드 생성이 아니라 **검증 루프**입니다.

### 색 대비 검증기 — 눈으로는 못 보는 결함을 잡았다

캔들 차트에 초록/빨강을 쓰는 것은 아무 생각 없이 지나갈 기본값입니다.
색을 눈으로 판단하지 않고 대비 검증기를 돌렸습니다.

```
$ node validate_palette.js "#0ca30c,#d03b3b" --mode dark --surface "#1a1a19"
  [FAIL] CVD separation   worst adjacent #d03b3b↔#0ca30c ΔE 4.1 (deutan)
  [PASS] Normal-vision    worst adjacent ΔE 33.9 (normal)
  → FAILED
```

정상 시각에서는 ΔE 33.9 로 잘 구분되는데 **적록색약에서 4.1 로 무너집니다.**
한국 남성의 약 5~6% 가 여기 해당합니다.

**중요한 것은 그다음 판단입니다.** 검증기는 "실패"라고만 말합니다. 초록/빨강을 버릴지는
사람이 정해야 하고, 저는 **버리지 않기로** 했습니다 — 모든 거래소가 쓰는 관례라
바꾸면 학습 비용이 생깁니다. 대신 색이 유일 채널이 되지 않게 했습니다
(부호·아이콘 병기, 캔들 몸통의 기하 인코딩). 자세한 내용은 [METRICS.md §4](METRICS.md).

검증은 자동화하고, **관례와 접근성 사이의 절충은 직접 정했습니다.**

### 가드레일 훅 — 프롬프트만 던지지 않았다

`.claude/hooks/` 에 두 개를 두었습니다.

- **타입체크 훅** — `.ts` 파일을 수정할 때마다 `tsc --noEmit` 을 돌립니다.
  AI 가 TypeScript 를 연속으로 쓰면 타입 오류가 조용히 누적되는데, 마지막에 한 번에
  터지면 어느 변경이 원인인지 찾기 어렵습니다. **쓰는 즉시 잡습니다.**
- **커밋 가드** — AI Co-Authored-By 트레일러를 차단합니다.
  트레일러는 "썼다"만 말할 뿐 "어떻게 썼는지"를 말하지 못합니다. 그 설명은 이 문서가 합니다.

두 훅 모두 저장소 밖의 파일에는 관여하지 않도록 경로 가드를 넣었습니다.

## 3. AI 가 만든 코드에서 실제로 나온 버그들

전부 **타입체크를 통과한 상태**였습니다. 도구를 어디까지 믿을 수 있는지에 대한 기록입니다.

### `sql<Date>` — 타입은 단언일 뿐 런타임 변환이 아니다

```ts
// 타입체크 통과. 런타임에 터진다.
const [row] = await db.select({ value: sql<Date>`max(open_time)` })...
row.value.getTime()   // ← value 는 실제로 문자열
```

`sql<T>` 는 TypeScript 단언이지 변환이 아닙니다. 하필 **백필 시작점을 정하는 함수**였고
**재시작할 때만** 터지는 버그였습니다. 단위 테스트로는 안 잡히고 통합 테스트에서 잡혔습니다.

> 배운 것: **타입은 경계 안쪽을 지키고, 경계에는 테스트를 둬야 한다.**
> DB·외부 API 처럼 타입 시스템이 닿지 않는 경계에는 반드시 실행 검증이 필요합니다.

### `ws_connected_since` 가 항상 NULL — "없음"에 두 가지 뜻이 섞였다

대시보드에 uptime 을 올리려고 DB 를 열어 보니 그 컬럼이 **항상 비어 있었습니다.**
연결 이벤트는 기록돼 있는데 값만 없었습니다.

원인은 부분 갱신 UPSERT 였습니다.

```sql
-- 안 준 필드까지 매번 null 로 덮어쓴다
ws_connected_since = excluded.ws_connected_since
```

연결 시 값을 써 넣지만, **1초마다 도는 티커 갱신이 그 필드를 안 넘기므로** 곧바로
null 로 덮였습니다. `last_error` 도 같은 구조라 기록되자마자 지워졌습니다.

"값 없음"에 **두 가지 뜻**(키를 안 줌 = 유지 / null 을 줌 = 삭제)이 있는데 하나로
뭉갠 것이 원인이었습니다. 키 존재 여부로 구분하고 회귀 테스트를 붙였습니다.

> 배운 것: **화면에 올릴 값을 실제로 꺼내 보기 전까지는 그 값이 있는지 모른다.**
> 이 버그는 대시보드를 만들지 않았으면 영영 발견되지 않았을 것입니다.

### 체결이 뜸한 심볼이 stale 로 보인다 — 실행해야만 보이는 버그

SSE 스트림을 흘려보니 BTCUSDT 는 lag 0.7초인데 **ETHUSDT 만 2초씩 계속 자랐습니다.**
소켓은 멀쩡했고 ETH 봉도 정상 수신 중이었습니다.

"마지막 수신 시각"이 두 뜻을 겸하고 있었습니다 — 연결 단위(watchdog 용)와
심볼별(대시보드용). 앞의 값을 뒤의 자리에 써넣는데, 쓰는 대상은 aggTrade 가 들어온
심볼뿐이었습니다. 체결이 잠시 뜸하면 kline 이 계속 들어와도 행이 갱신되지 않습니다.

> 배운 것: **정적 분석으로는 절대 안 나오는 종류의 버그다.** 실제로 띄우고
> 스트림을 눈으로 보는 단계가 없었으면 제출까지 갔을 것입니다.

### 집계 기준 시각이 심볼 필터 없이 잡혀 있었다

24시간 창의 기준을 "DB 의 마지막 봉"으로 잡았는데 **심볼 필터를 안 걸었습니다.**
심볼 하나가 정지하면 다른 심볼이 살아 있는 동안 정지한 쪽의 24시간 창이 통째로 빕니다.

실데이터에서는 두 심볼이 같이 살아 있어 **우연히 가려졌고**, 통합 테스트를 쓰면서
드러났습니다.

> 배운 것: **테스트가 실데이터보다 가혹한 조건을 만든다.** 실데이터는 정상 경로만 보여줍니다.

## 4. 검증기가 못 보는 것 — 렌더 후 육안 확인

색은 계산할 수 있지만 **축과 레이아웃은 눈으로 봐야 합니다.**
목업과 실제 화면을 브라우저로 렌더해 확인하는 단계에서 다음이 나왔습니다.
전부 타입체크와 색 검증기를 통과한 상태였습니다.

| 결함 | 원인 |
|---|---|
| Taker diverging bar 가 아무것도 안 보임 | 축을 ±100%p 로 잡아 실제 값(44~52%)이 중앙 1px 에 뭉갬 |
| "갭 복구 2,900봉" | 최초 적재(1,441봉×2)가 복구량에 합산됨 |
| 커버리지 미터가 안 그려짐 | 마운트 가드가 `h > 8` 인데 미터 높이가 정확히 8px |
| Hero 가 42px 대신 15px | 상위 셀렉터가 특이도로 `.hero .val` 을 이김 |
| 사이드바가 패널 밖으로 넘침 | 그리드 아이템 내용이 행 높이를 초과 |
| 현재가 태그와 y축 눈금 충돌 | 두 라벨이 같은 높이에 놓임 |
| 좌우 캔들 차트의 시작 높이가 어긋남 | 한쪽만 헤더가 두 줄이 됨 (두 심볼을 비교할 수 없게 됨) |
| 1366×768 에서 범례가 x축 라벨 위에 겹침 | 차트 호스트에 overflow 가 없었음 |

**목업을 더미가 아니라 실데이터로 만든 판단**이 여기서 회수됐습니다.
더미 값이었으면 "Taker 비율이 중앙에 뭉갠다"와 "갭 복구 2,900봉"은 발견되지 않았습니다.
둘 다 **실제 값의 분포 때문에** 드러난 문제입니다.

## 5. 다중 에이전트 코드 리뷰

구현이 끝난 뒤 코드 리뷰를 여러 관점의 에이전트에 분산해 돌리고, 각 지적을 **독립적인
검증자가 반박을 시도**하게 했습니다. 살아남은 10건 중 9건이 직전 커밋(컨테이너화)에
몰려 있었습니다. 가장 심각했던 둘:

**웹이 스키마 없는 DB 에 붙을 수 있었다** — 마이그레이션을 수집기 부팅의 부수효과로만
두고 있었습니다. 클린 클론에서 `docker compose up` 하면 웹이 먼저 떠서 500 을 내고,
수집기가 아예 못 뜨면 **대시보드가 영구히 죽습니다.** 마이그레이션을 별도 서비스로
분리했습니다.

**`.dockerignore` 가 없었다** — 개발 머신에서 빌드한 `.next` 캐시(Windows 절대 경로 기반)와
`.env.local` 이 이미지 빌드로 들어갔습니다. **같은 커밋이 내 머신과 클린 클론에서 다른
이미지를 만들 수 있었습니다.** 재현성이 이 프로젝트의 약속인데 그것부터 깨져 있었습니다.

> 이 둘은 **혼자 보면 놓치기 쉬운 종류**입니다. 내 머신에서는 둘 다 정상 동작하기 때문입니다.
> 리뷰를 컨테이너화 **직후**에 돌린 것이 맞았습니다 — 문서를 쓰고 배포까지 한 뒤였다면
> 전부 다시 해야 했습니다.

보안 리뷰도 별도로 돌렸습니다. `sql.raw()` 호출 경로, 파라미터 검증 일관성, SSE 프레임
주입, 스크립트의 `execFileSync` 를 추적한 결과 보고 기준을 넘는 취약점은 없었습니다.
(`pgTextArray` 는 raw SQL 싱크가 맞지만 환경변수에서만 값이 오고 형식 검사가 붙어 있습니다.)

## 6. 문서를 먼저 쓰고 코드를 나중에 썼다

설계 판단을 코드보다 먼저 문서로 남겼습니다 (`docs/DECISIONS.md`, 12개 항목).
각 항목은 **결정 / 배경 / 선택지 / 근거 / 비용** 구조입니다.

AI 와 일할 때 이게 특히 중요합니다 — 근거를 남기지 않으면 다음 세션에서
**이미 내린 결정을 다시 논의**하게 되고, 그때마다 결론이 조금씩 달라집니다.
세션이 바뀌어도 이어서 작업할 수 있도록 인수인계 메모(`docs/HANDOFF.md`)를 따로 두어
"다시 논의하지 않아도 되는 결정"을 명시했습니다.

공개 문서(이 문서와 ARCHITECTURE·METRICS)는 그 작업 노트를 **원본으로 다시 쓴 것**입니다.
작업 노트 자체는 제출 저장소에 포함하지 않습니다 — 과정의 기록과 결과물의 설명은
독자가 다르기 때문입니다.

## 7. 종합 — 무엇이 달라졌나

AI 없이 같은 시간을 썼다면 만들지 못했을 것:

- 색 대비 검증을 **돌려볼 생각 자체**를 못 했을 가능성이 높습니다. 초록/빨강은 너무 당연한 기본값입니다.
- 레이아웃 세 안을 **실데이터로** 만들어 비교하는 비용을 감당하지 못했을 것입니다.
  한 안만 만들고 그대로 갔을 것이고, markets 밴드가 헐겁다는 것도 몰랐을 것입니다.
- 다중 관점 코드 리뷰를 사람 한 명이 하기는 어렵습니다.

반대로 AI 가 만들어 준 것을 그대로 뒀다면 남았을 것:

- `ws_connected_since` 가 항상 NULL 인 채로 uptime 지표가 죽어 있었을 것입니다.
- Taker 비율 막대가 아무것도 안 보이는 채로 제출됐을 것입니다.
- 같은 커밋이 머신마다 다른 이미지를 만드는 상태로 "재현 가능합니다"라고 썼을 것입니다.

> **결론: AI 는 만드는 속도를 올렸고, 검증 장치는 만든 것을 믿을 수 있게 했습니다.**
> 둘 중 하나만 있었으면 이 결과물은 나오지 않았습니다.
> 가장 많이 한 일은 코드를 쓰는 것이 아니라 **"이게 정말 되는지 확인하는 방법"을 만드는 것**이었습니다.
