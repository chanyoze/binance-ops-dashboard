# 구조 설계

이 문서는 **무엇을 만들었는지**가 아니라 **왜 그렇게 만들었는지**를 씁니다.
무엇을 만들었는지는 코드가 말합니다.

---

## 1. 이 시스템이 푸는 문제는 하나다

과제는 세 가지를 요구합니다 — 최초 실행 시 과거 데이터 확보, 재시작 시 누락 구간 복구,
실시간 수집. 그런데 앞의 둘은 **같은 질문**입니다.

> "내가 가진 마지막 봉이 언제인가. 거기서부터 지금까지 채워라."

최초 실행은 "마지막 봉이 없다"는 특수한 경우일 뿐입니다. 그래서 함수를 하나만 만듭니다.

```ts
const last = await repo.getLastOpenTime(symbol, '1m')

const from = last ?? now - BACKFILL_DAYS * DAY
//           ↑ 이 한 줄이 "최초 백필"과 "재시작 갭 백필"을 가른다

await ensureRange(symbol, '1m', from, now)
```

과제 문장에 *"두 기능이 별개일 필요는 없습니다"* 라는 힌트가 있었고, 그대로 따랐습니다.

같은 함수가 네 상황을 처리합니다. 달라지는 것은 `reason` 하나뿐입니다.

| `reason` | 상황 | from | to | 호출 주체 |
|---|---|---|---|---|
| `initial` | 최초 실행 | `now - 7d` | `now` | 부팅 시퀀스 |
| `restart` | 서버 재시작 | DB 마지막 봉 | `now` | 부팅 시퀀스 |
| `reconnect` | WS 재연결 직후 | DB 마지막 봉 | `now` | 재연결 핸들러 |
| `scanner` | 중간 구멍 발견 | 구멍 시작 | 구멍 끝 | 무결성 스캐너 |

`reason` 은 동작을 바꾸지 않습니다. `pipeline_events` 에 기록되어 **왜 백필이 돌았는지**를
나중에 설명하는 용도입니다. 그리고 그것이 그대로 대시보드의 이벤트 로그가 됩니다.

### 재연결 복구가 "끊긴 시각"이 아니라 "DB 마지막 봉"에서 시작하는 이유

끊기기 직전 몇 초의 저장이 실패했을 수 있습니다. 끊긴 시각을 기준으로 잡으면 그 구간은
영영 복구되지 않습니다. **DB 를 진실로 삼으면** 그 경우까지 함께 복구됩니다.

## 2. 멱등성이 이 설계의 전제다

`ensureRange` 통합이 성립하는 이유는 **같은 구간을 몇 번 다시 긁어도 안전하기 때문**입니다.

```sql
PRIMARY KEY (symbol, interval, open_time)
INSERT ... ON CONFLICT (symbol, interval, open_time) DO UPDATE SET ...
```

이 제약 하나가 세 가지를 공짜로 해결합니다.

1. **백필 구간을 여유 있게 겹쳐 잡아도 된다** — 경계 계산을 정밀하게 할 필요가 없습니다.
   1분 정도 넉넉히 잡고 겹치게 두는 편이 오히려 안전합니다.
2. **백필과 실시간 수집이 같은 봉을 동시에 써도 된다** — 부팅 직후 백필이 도는 중에
   WS 가 붙어도 순서를 조율할 필요가 없습니다.
3. **미완성 봉이 확정 봉으로 자연히 덮인다** — WS 는 진행 중인 봉을 `isClosed: false` 로
   계속 보냅니다. 마지막에 `true` 로 오면 같은 키를 덮어씁니다. 별도 처리가 없습니다.

멱등성이 깨지면 위 셋이 전부 별도 로직이 되고, `ensureRange` 통합도 무너집니다.
그래서 통합 테스트에서 **가장 먼저 검증하는 것이 멱등성**입니다.

### `source` 컬럼 — 복구를 데이터로 증명한다

행마다 `'ws'` 인지 `'rest'` 인지 남깁니다. 이것이 있으면 "백필이 동작했다"를
말이 아니라 조회로 보일 수 있습니다.

```
13:14  ws    ← 죽기 전 실시간 수집
13:15  rest  ← 죽는 순간 미완성이던 봉을 백필이 확정본으로 덮음
13:16  rest  ┐
13:17  rest  ├ 죽어 있던 4분을 백필이 메움
13:18  rest  ┘
13:19  ws    ← 재시작 후 실시간 재개
```

대시보드의 "WS / REST 봉 수"도 여기서 나옵니다.

## 3. 수집기와 웹은 별도 프로세스다

```
   Binance                  ┌─────────────┐
   ├─ WebSocket  ──실시간──▶ │             │
   └─ REST API   ──백필───▶ │  collector  │ ──▶ ┌──────────┐
                            │   (워커)     │     │ Postgres │
                            └─────────────┘     └────┬─────┘
                                                     │ LISTEN/NOTIFY
                                              ┌──────▼──────┐
                                    브라우저 ◀─│   Next.js   │
                                        SSE   │   (웹)      │
                                              └─────────────┘
```

**생명주기가 다르기 때문입니다.**

| | collector | web |
|---|---|---|
| 재시작 | 하면 안 됨 (수집 중단) | 배포마다 함 |
| 복제 | 하면 안 됨 (중복 수집) | 트래픽 따라 해도 됨 |
| 상태 | 장기 WS 연결을 붙들고 있음 | 무상태 |

합쳐두면 **대시보드 CSS 한 줄 수정이 데이터에 구멍을 냅니다.** 배포할 때마다
WS 가 끊기고, 그때마다 갭이 생기고, 그 갭을 백필이 메우느라 REST weight 를 씁니다.

두 프로세스는 **서로를 직접 호출하지 않습니다.** Postgres 만이 유일한 접점입니다.
수집기는 웹의 존재를 모릅니다.

### 확장성

수집 심볼이 2개에서 200개로 늘면 수집기만 심볼 그룹별로 나누면 됩니다.
대시보드 트래픽이 늘면 웹만 복제하면 됩니다. 서로 영향을 주지 않습니다.

동봉한 `docker-compose.yml` 은 데모라 웹도 한 대로 고정(`container_name` + 고정 포트)했습니다.
실제로 복제하려면 그 둘을 빼고 앞에 로드밸런서를 두면 됩니다 — **코드는 그대로입니다.**
상태를 프로세스에 두지 않았기 때문입니다.

## 4. 장애 시나리오와 대응

| 장애 | 대응 | 어디에 있나 |
|---|---|---|
| WS 연결 끊김 | 지수 백오프 재연결 (1s → 최대 30s + jitter) | `backoff.ts` |
| Binance 의 24시간 강제 종료 | 위 재연결 로직이 그대로 흡수 — 별도 처리 없음 | — |
| **좀비 연결** (끊긴 걸 모름) | `lastMessageAt` watchdog, 10초 무소식이면 강제 재접속 | `ws-collector.ts` |
| 재연결 동안의 누락 | 재연결 직후 `ensureRange(reason=reconnect)` 자동 호출 | `ws-collector.ts` |
| 원인 불명의 누락 | 무결성 스캐너가 주기적으로 연속성 검사 후 자가 치유 | `integrity-scanner.ts` |
| REST rate limit | weight 카운터 + 응답 헤더 보정 + `Retry-After` 존중 | `weight-limiter.ts` |
| 프로세스 크래시 | `restart: unless-stopped` → 재시작 시 갭 백필 | `docker-compose.yml` |
| DB 일시 장애 | 버퍼를 두지 않음. **수집기는 살아남고** 구멍으로 남았다가 스캐너가 회수 | §5 |

### DB 가 죽어도 수집기는 죽지 않아야 합니다

위 표의 마지막 줄은 **한동안 사실이 아니었습니다.**

`pg` 의 커넥션 풀은 유휴 커넥션이 죽으면 pool 에 `error` 를 emit 하는데, 듣는 곳이
없으면 Node 가 처리되지 않은 예외로 올려 프로세스를 종료합니다. Postgres 를 정지시키자
`terminating connection due to administrator command` 가 그 경로로 올라와 **수집기가
그 자리에서 죽었습니다.** 표는 "구멍으로 남고 스캐너가 회수한다"고 말하는데, 정작
회수할 프로세스가 함께 죽고 있었던 것입니다.

데이터는 결과적으로 복구됐습니다 — Docker 가 되살렸고 부팅 백필이 메웠으니까요.
그래서 **겉으로는 아무 문제가 없어 보였습니다.** 컨테이너 기동 시각을 비교하고 나서야
드러났습니다.

지금은 커넥션 풀과 발행 커넥션 양쪽에서 오류를 받습니다. 죽은 커넥션은 풀이 알아서
버리고 다음 요청에 새로 만들므로, 우리가 할 일은 **프로세스를 지키는 것**뿐입니다.

`npm run demo:chaos -- --db` 가 이것을 검증합니다. 수집기가 재시작조차 하지 않는지를
컨테이너 기동 시각으로 확인하고, 그 구간의 구멍이 **재시작 없이** 메워지는지를 봅니다.
프로세스를 죽이는 시나리오는 부팅 시퀀스가 메우지만, 여기서는 수집기가 계속 살아 있으므로
부팅 백필이 돌지 않습니다 — 스캐너만이 회수할 수 있습니다.

### 가장 위험한 장애는 끊기는 것이 아니라 "끊긴 걸 모르는 것"이다

TCP 연결이 살아 있는데 데이터만 안 오는 상태가 있습니다. `onclose` 가 호출되지 않으므로
재연결 로직이 **영영 발동하지 않고**, 대시보드는 멀쩡한 얼굴로 몇 시간 전 값을 띄웁니다.
조용히 틀리는 것이 시끄럽게 죽는 것보다 나쁩니다.

그래서 마지막 메시지 수신 시각을 들고 있다가 임계를 넘으면 강제로 끊습니다.

```ts
if (Date.now() - lastMessageAt > STALE_THRESHOLD_MS) {
  socket.terminate()   // close() 가 아니다
}
```

`close()` 가 아니라 `terminate()` 인 이유 — 응답하지 않는 소켓은 close 핸드셰이크도
끝내지 못합니다. `close()` 를 부르면 그 자리에서 다시 멈춥니다.

**임계 10초의 근거:** BTCUSDT·ETHUSDT 는 Binance 에서 가장 거래가 활발한 심볼입니다.
aggTrade 는 초당 수 건~수십 건, kline 은 초당 1~2회 갱신됩니다. 10초간 무소식이면
정상 상황일 수 없습니다.

### 세 겹의 방어

같은 문제를 세 층에서 다르게 잡습니다. 하나가 실패해도 다음이 잡습니다.

```
1층  재연결 직후 갭 백필    ← 끊김을 인지한 경우
2층  무결성 스캐너          ← 인지하지 못한 누락
3층  프로세스 재시작 백필   ← 프로세스가 통째로 죽은 경우
```

스캐너는 **"왜 구멍이 났는지" 묻지 않습니다.** 주기적으로 훑어서 있으면 메웁니다.
원인별 대응 대신 상태 수렴으로 푸는 쪽이 원인이 하나 늘 때마다 코드가 늘지 않습니다.

## 5. 쓰기 버퍼도, 재시도 큐도 두지 않는다

DB 가 잠깐 죽으면 받은 데이터를 메모리에 붙들고 있어야 할까요? **아닙니다.**

> **원본이 Binance 에 남아 있습니다. Binance API 자체가 우리의 백업 저장소입니다.**

복구 가능한 원본이 외부에 있는데 자체 버퍼를 만드는 것은 이미 해결된 문제를
다시 만드는 일입니다. 버퍼를 두면 버퍼의 크기·만료·순서·중복을 관리해야 하고,
그 코드가 새로운 장애 지점이 됩니다.

그래서 DB 쓰기가 실패하면 **그냥 로그를 남기고 넘어갑니다.** 그 구간은 구멍으로 남고,
스캐너가 다음 주기에 회수합니다. 이미 있는 장치가 처리합니다.

### 이 판단이 성립하지 않는 경우 (한계)

- 원본이 외부에 없는 데이터라면 성립하지 않습니다. 우리가 유일한 사본이면 버퍼가 필요합니다.
- Binance 의 kline 조회 가능 기간을 넘겨 장애가 지속되면 그 구간은 복구할 수 없습니다.
- 초 단위 체결 원본을 보존해야 하는 요구가 생기면 재검토해야 합니다.

## 6. 1분봉만 수집하고 상위 인터벌은 SQL 집계로 만든다

5분봉·1시간봉을 각각 수집하지 않습니다. **1분봉만 저장하고 나머지는 `date_bin` 으로 접습니다.**

인터벌마다 수집하면 무결성 검증을 인터벌 수만큼 해야 하고, 같은 시각의 1분봉 5개와
5분봉 1개가 어긋나는 정합성 문제가 새로 생깁니다. 원본 해상도를 하나로 두면
**검증할 진실이 하나**입니다.

```sql
date_bin('5 minutes', open_time, timestamptz 'epoch')
```

기준점을 epoch 로 잡아야 Binance 의 봉 경계(:00, :05, …)와 어긋나지 않습니다.
데이터의 첫 시각을 기준으로 접으면 봉 경계가 **수집 시작 시각에 따라 달라집니다.**

비용은 조회 시 집계 부하입니다. 인덱스 `(symbol, interval, open_time DESC)` 로 커버되고,
24시간치가 심볼당 1,440행이라 문제되는 규모가 아닙니다.

## 7. 지표는 애플리케이션이 아니라 SQL 에서 계산한다

VWAP·이동평균·Taker 비율·커버리지·지수화 상대강도를 전부 SQL 에서 냅니다.

**대역폭 때문만이 아닙니다.** 1시간봉 24개를 보려고 1,440행을 내려보내는 것도 낭비지만,
더 나쁜 것은 **같은 지표가 화면마다 다르게 계산될 수 있다**는 점입니다.
정의를 SQL 한 곳에 두면 정의가 하나로 유지됩니다.

그리고 이것들은 `date_bin` 과 윈도우 함수로 Postgres 가 훨씬 잘하는 일입니다.
스키마를 `timestamptz` + `NUMERIC` 으로 잡아둔 값이 여기서 회수됩니다.

읽기 경로는 `AnalyticsRepository` 로 **쓰기 경로와 파일을 나눴습니다.** 쓰기는 멱등성과
정확한 한 행이 관심사고, 읽기는 집계와 응답 크기가 관심사입니다. 한 클래스에 두면
"차트가 필요해서" 수집 경로의 메서드를 고치는 일이 생깁니다.

### aggTrade 를 저장하지 않는 이유

Taker 매수 비율은 개별 체결을 모아야 나올 것 같지만, **Binance 가 kline 안에
`takerBuyBaseVolume` 으로 이미 집계해서 줍니다.** 그래서 aggTrade 원본이 필요 없습니다.

저장하지 않는 결정적 이유는 따로 있습니다 — aggTrade 는 `fromId` 기반 페이지네이션이라
**시간 기반 복구 모델과 맞지 않습니다.** 저장하면 "구멍을 시간으로 찾아 시간으로 메운다"는
모델 밖에 있는 복구 경로가 하나 더 생깁니다.

받기는 받습니다. 틱 최신가를 `collector_state.last_price` 에 갱신하는 데 씁니다 —
1분봉보다 최대 60초 앞선 가격입니다. 받아서 쓰고 버립니다.

## 8. 실시간 전송 — LISTEN/NOTIFY → SSE

수집기(별도 프로세스)가 새 데이터를 받았을 때 웹 서버가 어떻게 알 것인가.

```
[collector] ──LISTEN/NOTIFY──▶ [web] ──SSE──▶ [browser]
```

**Postgres LISTEN/NOTIFY** 를 쓴 이유는 인프라를 하나도 늘리지 않으면서 진짜 push 를
구현하기 때문입니다. 웹이 1초마다 "새거 있어?"를 묻지 않아도 됩니다.
Redis 를 추가하면 컨테이너가 하나 늘고, 채점자가 실행할 때 실패할 수 있는 지점도 하나 늡니다.

`RealtimeBus` 인터페이스로 감싸 둔 이유가 핵심입니다 — 규모가 커지면 Redis Pub/Sub 으로
교체해야 하는데, 그때 **바꿔야 할 것이 그 파일 하나**입니다.
확장성에 대한 고민을 말이 아니라 코드 구조로 남긴 것입니다.

**브라우저로는 SSE** 를 씁니다. 이 화면의 통신은 서버→클라이언트 단방향이고,
브라우저가 서버로 보낼 말이 없습니다. SSE 는 그 경우를 위한 프로토콜이면서 두 가지를
공짜로 줍니다 — 재연결이 브라우저에 내장돼 있고, 평범한 HTTP 라 프록시를 그냥 통과합니다.
WebSocket 은 양방향을 얻는 대신 그 둘을 직접 만들어야 합니다.

### SSE 허브는 프로세스당 하나다

`PgNotifyBus` 는 LISTEN 전용 커넥션을 하나 붙들고 삽니다. 브라우저 탭마다 버스를 만들면
탭 수만큼 커넥션이 열려 `max_connections` 에 닿습니다. **구독은 한 번, 팬아웃은 메모리에서**
합니다. 참조 카운트로 켜고 꺼서 보는 사람이 없으면 DB 부하가 0 입니다.

### 끊겼다 붙는 동안 놓친 것

SSE 재연결은 브라우저가 해주지만 **끊긴 동안의 데이터는 오지 않습니다.** 그래서 재연결 시
초기 페이로드를 한 번 다시 받아 상태를 맞춥니다 — 수집기가 갭을 백필하는 것과 같은 발상입니다.

### 열려 있는데 아무것도 오지 않을 때

`EventSource` 는 응답 **헤더**를 받은 시점에 `open` 을 냅니다. 본문이 한 바이트도 오지
않아도 마찬가지입니다. 그래서 중간 프록시가 스트림을 버퍼링하면 **연결됨으로 표시된 채
영원히 아무것도 받지 못하는** 상태가 됩니다. 오류도 나지 않고 재연결도 걸리지 않습니다.
화면은 멈춰 있는데 자기가 멈췄다는 것을 모릅니다.

수집기의 좀비 연결 문제와 같습니다 (§4) — 소켓은 OPEN 인데 메시지만 오지 않는 상황.
그래서 같은 방식으로 풉니다. **마지막 이벤트로부터 8초**가 지나면 멎은 것으로 보고,
상태를 `stalled` 로 바꾼 뒤 **5초 간격으로 초기 페이로드를 다시 받습니다.**

8초인 이유는 운영 지표가 2초마다 밀려오기 때문입니다. 그것을 네 번 놓친 것은 정상
변동으로 보기 어렵습니다. heartbeat(15초)는 기준으로 쓸 수 없습니다 — SSE 주석 줄이라
`EventSource` 가 이벤트로 노출하지 않습니다.

세 가지를 지킵니다.

- **끊긴 것과 멎은 것을 나눕니다.** 끊긴 경우(`reconnecting`)에는 폴링하지 않습니다.
  연결이 없으면 폴링도 실패하고, 그때는 브라우저가 알아서 다시 붙습니다.
- **폴백은 멎었을 때만 돕니다.** `/api/dashboard` 는 커버리지·상대강도·24h 집계를 전부
  도는 무거운 경로입니다. 헬스체크를 따로 가볍게 만든 이유와 정면으로 충돌하므로,
  정상 환경에서는 한 번도 실행되지 않게 했습니다. 멎은 상황에서만은
  "무거워도 갱신되는 화면"이 "가벼운데 멈춘 화면"보다 낫습니다.
- **표시가 사실을 말합니다.** 멎은 상태를 `live` 로 두면 화면이 조용히 거짓말합니다.
  그것은 아무 표시도 없는 것보다 나쁩니다.

Cloudflare 터널 뒤에서 실제로 재현했습니다(70초 동안 0바이트). 사내 프록시와 일부 CDN 이
같은 동작을 합니다. 판정 로직은 순수 함수로 분리해 테스트합니다(`lib/stream-health.ts`).

### 한계

LISTEN 은 커넥션이 계속 살아 있어야 하므로 **서버리스 환경에서는 동작하지 않습니다.**
Vercel 에 올린다면 폴링으로 바꿔야 합니다. 컨테이너로 배포하는 전제에서 선택했습니다.

## 9. 기동 순서

```
postgres (healthy)  →  migrate (정상 종료)  →  collector · web
```

마이그레이션을 **수집기 부팅의 부수효과로 두지 않았습니다.** 그러면 수집기가 못 뜨는 상황
(네트워크 차단, 크래시 루프)에서 스키마가 영영 생기지 않고 대시보드까지 함께 죽습니다.
두 프로세스가 공통으로 의존하는 단계이므로 별도 서비스로 올렸습니다.

수집기 코드에 `runMigrations` 는 남겨 뒀습니다 — compose 밖에서 단독 실행할 때를 위한
것이고, 마이그레이션은 멱등이라 두 번 돌아도 안전합니다.

## 10. 데이터 모델

```sql
klines(symbol, interval, open_time, close_time,
       open, high, low, close, volume, quote_volume, trade_count,
       taker_buy_base, taker_buy_quote,
       is_closed, source, updated_at)
  PRIMARY KEY (symbol, interval, open_time)
  INDEX (symbol, interval, open_time DESC)

pipeline_events(id, ts, symbol, type, detail jsonb)
  INDEX (ts DESC), (type, ts DESC)

collector_state(symbol, interval, last_open_time,
                last_price, last_price_at, last_message_at,
                ws_connected_since, reconnect_count, last_error, updated_at)
```

**설계 원칙 세 가지**

1. **가격·수량은 전부 `NUMERIC`.** `double precision` 을 쓰면 시세에 오차가 생깁니다.
   Drizzle 이 `numeric` 을 문자열로 다루므로 애플리케이션까지 정밀도가 보존됩니다.
   `pg` 의 타입 파서도 명시적으로 문자열로 고정했습니다 — 여기서 number 로 바뀌면
   생기는 오차는 조용해서 한참 뒤에야 발견됩니다.
2. **시각은 전부 `timestamptz`(UTC).** 집계를 SQL 에서 하기로 했으므로 `date_bin`·
   윈도우 함수를 그대로 쓸 수 있는 타입이어야 합니다. Binance 는 epoch ms 를 주므로
   변환은 **리포지토리 경계 한 곳에서만** 일어납니다.
   저장·로그는 UTC 이고 **화면과 `demo:chaos` 출력만 KST 로 적습니다** — 운영 화면이
   답해야 하는 첫 질문("얼마나 최신인가")의 기준이 보는 사람의 벽시계이기 때문입니다.
   표시 시간대는 `apps/web/src/lib/format.ts` 한 곳에 고정돼 있고, 원본 UTC 가 필요한
   자리(캔들 툴팁)에는 두 값을 함께 적습니다.
3. **`pipeline_events` 는 로그가 아닙니다.** 로그는 사람이 터미널에서 보는 것이고,
   이 테이블은 **대시보드가 읽는 운영 지표**입니다. 자가 치유가 실제로 동작했다는
   증거가 여기 쌓입니다.

| 수집기 | Node.js 독립 워커 | 장기 실행 WS 연결은 웹 서버와 생명주기가 다릅니다 (§3) |
| 웹 | Next.js (App Router) | 서버 컴포넌트로 초기 데이터를 채우고 Route Handler 로 API 를 한 프로젝트에서 해결 |
| DB | PostgreSQL 16 | 시계열 UNIQUE 제약 + UPSERT + `date_bin` + 윈도우 함수 |

| 차트 | 직접 구현 (SVG) | 필요한 것이 캔들·라인·다이버징 바 셋뿐이라, 라이브러리를 들이는 것보다 마크 규격을 쥐는 편이 낫습니다 |
| 실시간 | LISTEN/NOTIFY → SSE | §8 |
| 패키지 매니저 | npm workspaces | 채점자가 `npm install` 만으로 재현할 수 있습니다. pnpm 은 사전 설치를 요구합니다 |

### 왜 시계열 DB(InfluxDB 등)가 아닌가

시세 데이터라서 시계열 DB 가 먼저 떠오르는 것이 자연스럽습니다. 검토했고, 쓰지 않기로
했습니다. 근거를 무게 순으로 적습니다.

**1. 이 시스템의 핵심은 쓰기 성능이 아니라 멱등성입니다.**
설계의 척추가 `ON CONFLICT DO UPDATE` 입니다(§2). InfluxDB 도 같은
`(measurement, tag set, timestamp)` 에 쓰면 값이 덮이지만, 그것은 *last write wins* 이지
**명시적인 upsert 의미론이 아닙니다.** 특히 이 프로젝트는 *"키를 안 주면 유지,
명시적 null 이면 삭제"* 라는 **부분 갱신**이 필요했는데(수집기 상태 갱신), 그것은
`SET` 절이 있어야 표현됩니다. 실제로 그 구분을 뭉갰다가 uptime 지표가 통째로
죽은 적이 있습니다.

**2. 집계를 SQL 에서 한다는 결정(§7)과 한 몸입니다.**
이동평균은 윈도우 함수, 1분봉 롤업은 `date_bin`, WS/REST 구분은 `count(*) filter`,
운영 지표는 조인으로 만듭니다. 다른 질의 언어로도 가능하지만, **지표 정의를 한 곳에
두겠다는 결정**을 가장 적은 마찰로 지킬 수 있는 쪽을 골랐습니다.

**3. 규모가 시계열 DB 를 요구하지 않습니다.**
2심볼 · 1분봉 · 7일 = 약 2만 행, 5MB 대입니다. 심볼을 200개로 늘려도 하루 28만 행
수준입니다. 압축·다운샘플링·보존 정책이라는 시계열 DB 의 이점이 발동할 스케일이
아닙니다. **여기서 이점이 없는 도구를 들이면 남는 것은 운영 비용뿐입니다.**

**4. 인프라를 늘리지 않습니다.** Redis 대신 `LISTEN/NOTIFY` 를 택한 것과 같은 논리입니다(§8).
컨테이너가 하나 늘면 채점자가 실행에 실패할 지점도 하나 늡니다.

**5. 운영 지표와 시세가 한 DB 에 있습니다.** `pipeline_events` 는 관계형이 자연스럽고
대시보드가 둘을 함께 읽습니다. 저장소를 나누면 그 조인이 애플리케이션으로 올라옵니다.

**6. (후순위이지만 실제로 작용한 이유) 회사가 쓰는 스택입니다.**
채용 공고의 기술 스택에 PostgreSQL 은 있고 InfluxDB 는 없습니다. 기술적으로 우열이
갈리지 않는 지점이라면 **읽는 사람이 이미 아는 도구**를 고르는 편이 낫다고 판단했습니다.
이것만으로 고른 것은 아니지만, 선택에 실제로 영향을 준 요소라 숨기지 않고 적습니다.

**언제 시계열 DB 가 맞는가** — 초당 수만 포인트를 쓰거나, 원본 tick 을 장기 보관하며
자동 다운샘플링·보존 정책이 필요하거나, 수년치를 압축해야 할 때입니다. 이 과제는 셋 다
아닙니다. 특히 **aggTrade 원본을 저장하지 않기로 한 결정(§7)이 결정적입니다** —
개별 체결을 전부 적재했다면 판단이 달라졌을 수 있습니다.

**확장 경로는 TimescaleDB 입니다.** PostgreSQL 확장이라 같은 SQL 로 하이퍼테이블과
continuous aggregate 를 얻습니다. 저장소를 갈아타는 **마이그레이션이 아니라 확장**이라는
점이 요점입니다 — 지금의 선택이 나중의 선택지를 좁히지 않습니다.

## 13. 알려진 한계 — 그리고 넘는 방법

한계를 적되 넘는 방법까지 적습니다. 여기 있는 것들은 몰라서 남은 것이 아니라
과제 범위에서 의도적으로 멈춘 지점이고, 넘을 자리는 설계에 미리 내 두었습니다.

- **수집기는 단일 인스턴스 전제입니다.** 복제하면 같은 심볼을 두 번 받습니다.
  → 확장의 축을 **심볼**로 잡아 두었습니다. 심볼은 코드에 박히지 않고 `SYMBOLS`
  환경변수로만 들어오므로, 워커마다 다른 묶음을 주면 그대로 수평 확장됩니다.
  한 심볼을 두 워커가 잡는 것만 막으면 되고, 그건 배치 구성의 문제입니다.
  자동 재분배까지 필요해지는 규모라면 그때 조정 계층(리스 기반 파티션 할당)을 얹습니다.
- **LISTEN/NOTIFY 는 서버리스에서 못 씁니다** (§8).
  → `RealtimeBus` 인터페이스 뒤에 두었으므로 Redis Pub/Sub 구현으로 갈아끼우면
  나머지 코드는 그대로입니다. 교체 지점을 미리 만들어 둔 것이 이 한계에 대한 답입니다.
- **NOTIFY 페이로드 상한이 8KB** 입니다. 넘으면 알림만 보내고 본문은 생략하며,
  수신 측이 DB 를 다시 읽습니다. 정합성은 유지되지만 그 경우 지연이 늘어납니다.
- **웹 API 에 인증이 없습니다.** 공개 시장 데이터만 읽고 쓰기 경로가 없는 단일 테넌트
  대시보드 전제입니다. 외부에 공개한다면 인증이 필요합니다.
  → **쓰기 경로가 없다**는 것이 요점입니다. 권한 모델을 설계할 필요 없이 읽기 인증
  한 겹만 앞에 두면 됩니다. Postgres 포트도 루프백에만 묶여 있습니다.
- **웹 빌드만 webpack 을 씁니다.** 워크스페이스 패키지가 TypeScript ESM 표준대로
  상대 임포트에 `.js` 를 붙이는데(실제 파일은 `.ts`) Turbopack 이 아직 그 치환을
  하지 않습니다. Turbopack 이 지원하면 플래그만 지우면 됩니다.
- **실제 Binance 연결 자체는 테스트하지 않습니다.** 재연결·watchdog·갭 복구는 가짜 소켓과
  가짜 타이머로 검증하고, 진짜 네트워크를 타는 경로는 `npm run demo:chaos` 로 확인합니다.
  둘 중 하나만으로는 부족합니다 — 단위 테스트는 "판단이 맞는가"를, chaos 는
  "실제로 동작하는가"를 봅니다.
