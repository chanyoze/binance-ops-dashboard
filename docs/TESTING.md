# 검증 방식 — 테스트를 어떻게 고르고, 그 테스트를 무엇으로 검증하는가

이 문서는 "테스트를 몇 개 썼다"를 말하지 않습니다. **무엇을 테스트하기로 했고, 그 테스트가
실제로 무언가를 지키는지 어떻게 확인했는지**를 적습니다.

```bash
npm run typecheck      # 경계 안쪽
npm test               # 228건 (단위 195 + 통합 33)
npm run test:mutate    # 그 테스트가 실제로 무엇을 지키는지
npm run demo:chaos     # 진짜 네트워크·프로세스를 태우는 경로
```

---

## 1. 출발점 — 통과는 아무것도 말해주지 않는다

아무것도 검증하지 않는 테스트도 통과합니다. 이 저장소에서 실제로 **두 번** 나왔습니다.

**하나.** "구독자 하나가 터져도 나머지 전송은 계속된다"는 테스트가, 로컬 배열에 함수 두 개를
만들어 **테스트가 스스로 try/catch 로 돌리고** 결과를 확인하고 있었습니다. 모듈의
`broadcast()` 는 한 번도 호출되지 않았습니다. 즉 **거기 있는 try/catch 를 통째로 지워도
이 테스트는 통과합니다.** 초록불이 켜져 있었을 뿐 지키는 것이 없었습니다.

**둘.** rate limit 테스트에서 "아직 대기 중인가"를 확인하는 헬퍼를
`Promise.race([p.then(...), Promise.resolve(marker)])` 로 짰습니다. 이미 끝난 약속이어도
마커 쪽이 한 틱 빠릅니다. 그 헬퍼는 **항상 "대기 중"이라고 답했고**, 그것을 쓴 단언 세 개가
전부 무의미했습니다.

둘 다 코드 리뷰를 통과했고, 둘 다 **일부러 망가뜨려 보고 나서야** 드러났습니다.
그래서 이 저장소는 테스트를 붙이는 것으로 끝내지 않고, 그 테스트를 한 번 더 검증합니다.

## 2. 무엇을 테스트할지 고르는 기준

**커버리지를 올리려고 고르지 않습니다.** 다음 두 부류만 고릅니다.

| 부류 | 뜻 | 예 |
|---|---|---|
| **데이터에 구멍이 나는 곳** | 여기가 틀리면 수집이 멈추거나 봉이 비는데, 나중에야 안다 | 갭 계산, UPSERT 멱등성, weight 관리, 재연결·watchdog |
| **화면이 조용히 거짓말하는 곳** | 오류도 로그도 없이 틀린 값을 맞다고 보여준다 | 지표 정의, 봉 병합, 표시 시간대, Lag 임계, 스트림 상태 표시 |

공통점은 **틀려도 시끄럽지 않다**는 것입니다. 부팅이 실패하는 종류(설정 파싱 등)는
테스트하지 않습니다 — 틀리면 그 자리에서 시끄럽게 죽으므로 이미 안전합니다.

### 특히 신경 쓴 두 지점

**타입이 닿지 않는 경계.** Binance 응답 파싱은 REST 가 배열 인덱스(`row[9]`, `row[10]`),
WS 가 한 글자 키(`k.v`, `k.q`, `k.V`, `k.Q`)로 읽습니다. 바꿔 써도 타입은 통과하고 파싱도
성공하고 저장도 됩니다. 화면에는 그럴듯한 숫자가 뜹니다.

그중에서도 가장 중요한 것은 **두 파서의 등가성**입니다. 같은 봉을 서로 다른 값으로 만들면
WS 가 저장한 봉을 백필이 덮어쓰면서 UPSERT 멱등성이 깨지고, `ensureRange` 하나로 네 가지
복구 경로를 처리하는 설계 전체가 무너집니다. 그 붕괴도 조용합니다.

**순수 함수와 I/O 의 분리.** 판단(갭 산정, 백오프, 스트림 상태, 봉 병합)은 순수 함수로 빼서
결정적으로 테스트하고, 배선은 따로 봅니다. 그래서 React 훅에서도 "핸들러 하나에서 수신
신호를 빠뜨리면 정상인데도 무거운 폴링이 상시로 도는" 종류를 잡을 수 있습니다.

## 3. 계층마다 사각이 있습니다

| 계층 | 보는 것 | **못 보는 것** |
|---|---|---|
| 타입체크 | 경계 안쪽의 형태 | 런타임 값. `sql<Date>` 는 단언일 뿐 변환이 아닙니다 |
| 단위 테스트 | 판단이 맞는가 | 진짜 네트워크·DB·브라우저 |
| 통합 테스트 | DB 와의 계약 | 축·레이아웃 같은 시각 결함 |
| 육안 검수 | 축·겹침·스케일 | 색 대비처럼 눈으로 못 재는 것 |
| 색 대비 검증기 | 색 | 다른 모든 것 |
| **환경** | 프록시·컨테이너 뒤에서의 동작 | — |

**마지막 줄이 가장 늦게 알았습니다.** SSE 라우트가 붙인 `Cache-Control: no-transform` 을
`next.config.ts` 의 일괄 규칙이 덮고 있었는데, 로컬에서는 증상이 **전혀** 없습니다.
중간에 프록시가 없기 때문입니다. 타입체크도, 테스트도, 두 차례의 코드 리뷰도 잡지 못했습니다 —
셋 다 **코드만** 보기 때문입니다. 실제로 프록시 뒤에 올려 보고서야 드러났고,
그때의 증상은 화면이 오류 없이 조용히 멈추는 것이었습니다.

> **검증 계층마다 사각이 있고, 마지막 사각은 "환경"입니다.**

## 4. 변이 검증 — 테스트를 테스트합니다

```bash
npm run test:mutate           # 전부
npm run test:mutate -- --list # 목록만
```

각 항목은 **"이 코드가 이렇게 틀리면 이런 일이 난다"** 를 실행 가능한 형태로 적은 것입니다.
스크립트가 코드를 일부러 망가뜨리고, 대상 테스트를 돌리고, **실패하는지** 확인한 뒤
원본을 되돌립니다. 빠져나가는 변이가 하나라도 있으면 종료 코드 1 로 끝납니다.

```
  [1/17] rest-taker-swap            잡힘
  [2/17] ws-volume-swap             잡힘
  ...
  ✓ PASS — 변이 17건이 모두 잡혔습니다.
```

지금 검증하는 17건은 이런 것들입니다.

| 변이 | 망가지면 생기는 일 |
|---|---|
| REST 의 taker 기초/견적 자산 맞바꿈 | Taker 비율이 통째로 틀린데 화면은 그럴듯합니다 |
| WS 의 `v`/`q` 맞바꿈 | 글자 하나 차이. 사람이 가장 틀리기 쉽습니다 |
| 4xx 재시도 | 결과가 같은 요청을 반복해 rate limit 을 태우고 구멍이 넓어집니다 |
| weight 소프트 임계 무시 | 429/418 → 백필 정지 → 그 구간이 구멍 |
| 무결성 스캐너의 심볼 격리 제거 | 앞 심볼의 실패가 뒤 심볼의 스캔을 데려갑니다 |
| 좀비 연결 종료 후 재연결 미예약 | 끊는 것으로 끝나면 수집은 멈춘 채입니다 |
| 실시간 봉을 덮지 않고 누적 | 1분에 60개가 쌓여 시간 축이 어긋납니다 |
| 스트림 멎음 판정 무력화 | 화면이 "연결됨"이라고 말한 채 영원히 멈춥니다 |
| 훅에서 수신 신호 누락 | 정상인데도 무거운 집계 폴링이 상시로 돕니다 |
| SSE 시작 실패 시 구독자 미회수 | 허브가 다시는 멈추지 않습니다 |
| 심볼 화이트리스트 해제 | 수집하지 않는 문자열이 조회 경로로 들어갑니다 |
| 표시 시간대 되돌리기 | 시각이 아홉 시간 밀려도 화면은 멀쩡합니다 |
| Lag 임계 이동 | 위험한 상태가 정상 색으로 뜹니다 |
| 채널명 검증 순서 되돌리기 | 잘못된 이름 하나가 재구독 전체를 영구히 막습니다 |
| **UPSERT 를 DO NOTHING 으로** | 이 설계의 **전제**입니다. 미완성 봉이 확정 봉으로 덮이지 않고 영구히 고착됩니다 |
| 갭 판정 무력화 | 구멍을 못 찾으면 스캐너가 아무것도 회수하지 않습니다 — 마지막 방어선이 사라집니다 |

`--list` 로 각 항목의 사유를 볼 수 있습니다.

## 5. 이 절차가 실제로 잡은 것

주장이 아니라 기록입니다. 전부 커밋에 남아 있습니다.

| 무엇 | 어떻게 드러났나 |
|---|---|
| 테스트가 자기 자신을 검증 | 코드 리뷰 |
| 대기 판정 헬퍼가 항상 "대기 중" | **변이 검증** (기본값을 60초→1초로 바꿨는데 12건이 그대로 통과) |
| 라우트 테스트가 우연히 통과 | **변이 검증** (설정이 마침 `'1m'` 이라 하드코딩해도 통과) |
| 무결성 스캔의 심볼 격리 없음 | 코드 리뷰 |
| SSE 구독 누수 3종 | 코드 리뷰 |
| 가짜 소켓이 실제 `ws` 와 다름 | 코드 리뷰 |
| `no-transform` 이 나가지 않음 | **환경** (프록시 뒤에 올려 보고) |
| `EventSource` 가 헤더만 받아도 `open` | **환경** |
| 채널명 검증이 등록보다 나중 | 테스트를 쓰다가 |
| 상대 강도 라벨 겹침 | **육안 검수** (스크린샷) |
| DB 가 죽자 수집기까지 죽음 | **장애 주입** (`demo:chaos --db` 를 만들다가) |
| 초록/빨강의 색약 대비 부족 | **색 대비 검증기** (정상 ΔE 33.9 / 색약 4.1) |

같은 계층이 두 번 잡은 적은 거의 없습니다. **계층을 늘린 만큼 잡혔습니다.**

## 6. 실행 방법

```bash
# 전체 (Postgres 필요)
docker compose up -d postgres && npm run db:migrate
npm run typecheck && npm test && npm run test:mutate

# DB 없이 — 단위 테스트만 돌고 통합 33건은 조용히 스킵됩니다
npm test
```

통합 테스트가 DB 없이 조용히 넘어가는 것은 의도한 설계입니다. 이 저장소를 처음 받은 사람이
Postgres 를 띄우지 않고 `npm test` 를 돌려도 막히지 않아야 합니다.
[CI](../.github/workflows/ci.yml) 는 그 약속이 지켜지는지도 함께 확인합니다 —
DB 없이 한 번, 통합까지 한 번, 그리고 변이 검증까지 세 단계로 돌립니다.

`npm run demo:chaos` 는 이 문서의 범위 밖입니다. 그것은 코드를 검증하는 것이 아니라
**진짜 프로세스를 죽였다 살려서** 복구를 확인하는 절차이고, [README](../README.md) 에 있습니다.
